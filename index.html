SOAP, REST, GraphQL and gRPC all carry the same data. What separates them is how much they wrap it in, how fast it travels, and how much they ask of the client on the other end.

SOAP XML envelope · heaviest payload
REST JSON over HTTP · cacheable
GraphQL only the fields asked for
gRPC binary over HTTP/2 · fastest

Line thickness and speed stand for payload size and latency — the trade-off this whole page is about.

01

Four different kinds of answer

Only two of these are really the same kind of thing. SOAP is a protocol and gRPC is a framework — both prescribe how you must talk. REST is a set of architectural constraints, and GraphQL is a query language that runs on one endpoint.

SOAP

W3C · 1.2 since 2003

A strict XML messaging protocol. The contract lives in a WSDL file, and the WS-* stack adds security, reliable delivery and distributed transactions.

REST

Fielding · 2000

An architectural style, not a product. Data becomes resources with URIs, and HTTP verbs and status codes carry the operation and its outcome.

GraphQL

Meta · open since 2015

A typed schema plus a runtime. The client sends a query describing exactly the fields it wants and gets back that shape, nothing more.

gRPC

Google · 2015

Remote procedure calls over HTTP/2. Messages are binary Protocol Buffers, and client and server stubs are generated from a .proto file.

The first table covers how each one is built; the second covers what it is like to live with. Hover a column heading to read one architecture on its own.

Twelve criteria in total — six structural, six operational.

03

What each one gives you, and what it costs

No architecture is free. Every strength listed on the left is paid for by something on the right.

SOAP

Gives you

  • A formal, machine-readable contract
  • Standards for message-level security, reliable delivery and distributed transactions
  • Independence from the transport

Costs you

  • Verbose messages that are slow to parse
  • A steep learning curve and heavy tooling
  • A poor fit for browsers and mobile networks

REST

Gives you

  • Simplicity — testable from a browser or curl
  • Caching, proxies and CDNs that work out of the box
  • Statelessness, so instances scale horizontally

Costs you

  • No contract unless you add OpenAPI
  • Over-fetching and under-fetching
  • Several round trips for related data

GraphQL

Gives you

  • Exactly the fields the client asks for
  • One endpoint covering many resources
  • A typed, self-documenting schema

Costs you

  • HTTP caching, which is lost
  • The N+1 resolver problem without a data loader
  • Depth and complexity limits against hostile queries

gRPC

Gives you

  • The highest throughput and lowest latency
  • Type-safe generated stubs in many languages
  • Streaming, deadlines and cancellation as first-class features

Costs you

  • Readability — binary payloads are hard to debug
  • A proxy layer before a browser can call it
  • HTTP/2 all the way through the stack
04

The system we are designing for

A Student Management System for a university: enrollment, timetables, grades and transcripts, used by students, staff and other campus systems.

Core resources

Students, lecturers, courses, class sections, enrollments, grades, transcripts and timetables. Almost every entity is a record that gets created, read, updated and listed.

Clients

A student web portal, a staff admin portal, a mobile app, and third-party campus systems such as the LMS, the library and a payment gateway.

Traffic

Read-heavy. Catalogue, timetable and grade lookups dominate day to day, while writes arrive in short bursts during the enrollment window each semester.

What matters

Easy integration for other campus systems, low build and maintenance cost, effective caching, standard authentication, and documentation a new developer can follow.

Nothing in this profile calls for distributed transactions, message-level signing, sub-millisecond latency or long-lived streams — which is exactly what rules three of the four candidates out.

05

The architecture we chose

REST over HTTPS · JSON · OpenAPI 3.1

It is the only one of the four whose strengths line up with a read-heavy, integration-heavy campus system, and whose weaknesses can be paid off with a few well-known patterns.

  1. The domain is already resource-orientedStudents, courses and enrollments map onto URIs and HTTP verbs with almost no translation.
  2. Read-heavy traffic gets caching for freeCatalogues and timetables change rarely, so ETag and Cache-Control let browsers and proxies absorb most reads.
  3. Every client can reach itWeb, mobile and external campus systems all speak plain HTTP — no proxy, no special client library.
  4. Lowest cost to build and hand overSpring Boot with springdoc-openapi produces a documented, testable API in days rather than weeks.
  5. Standard security and ecosystemTLS, OAuth2 and JWT, role checks per endpoint, and mature tooling: Swagger UI, Postman, gateways, rate limiting.
  6. Fast enough for the jobPayloads are small records, not high-frequency streams, so REST's overhead is irrelevant at campus scale.

Why not SOAP

Its transactional and message-security guarantees are not needed here, and the XML overhead hurts exactly the mobile clients we care about.

Why not GraphQL

Its flexibility pays off across many heterogeneous sources, and it would cost us the HTTP caching this read-heavy system depends on.

Why not gRPC

Excellent between internal services, but a poor public edge: browsers need a proxy and the binary format resists debugging and integration.

The honest trade-off. REST over-fetches and can need extra round trips. We pay that down with sparse fieldsets, sub-resource endpoints, pagination and optional expansion. If the mobile app later needs highly variable payloads, a GraphQL gateway can sit in front of the same services without touching them.

openapi.yaml — the contract REST does not give you for free

            
openapi: 3.1.0
info:
  title: Student Management API
  version: 1.0.0
servers:
  - url: https://api.university.edu/v1
paths:
  /students/{studentId}:
    get:
      summary: Get a student by ID
      security: [{ bearerAuth: [] }]
      parameters:
        - name: studentId
          in: path
          required: true
          schema: { type: string, pattern: '^[A-Z]{2}\d{6}$' }
      responses:
        '200':
          description: Student found
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Student' }
        '404': { description: Student not found }
components:
  schemas:
    Student:
      type: object
      required: [studentId, fullName, major, status]
      properties:
        studentId:      { type: string, example: 'SE170123' }
        fullName:       { type: string }
        email:          { type: string, format: email }
        major:          { type: string }
        enrollmentYear: { type: integer, minimum: 2000 }
        status:
          type: string
          enum: [ACTIVE, SUSPENDED, GRADUATED]
  securitySchemes:
    bearerAuth: { type: http, scheme: bearer, bearerFormat: JWT }

08

        

          
What we take away

        

      

      
    
        
  • The four architectures solve different problems. SOAP gives contracts and enterprise guarantees,
          REST gives simplicity and reach, GraphQL gives client-driven queries, gRPC gives speed and streaming.
    • 
        
  • There is no universally best option. The choice follows the clients, the shape
          of the data and the traffic profile — not fashion.
    • 
        
  • For a Student Management System, REST wins on client reach, cacheability and
          cost of development, and its weaknesses are cheap to mitigate.
    • 
        
  • A mature system usually mixes them: REST at the public edge, gRPC between
          internal services once the system is split up, and a GraphQL gateway in front if mobile clients need highly
          variable payloads.
