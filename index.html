Definitions

Four different kinds of answer

Only two of these are directly comparable. SOAP is a protocol and gRPC is a framework — both prescribe how you must talk. REST is a set of architectural constraints, and GraphQL is a query language that runs on top of one endpoint.

SOAP

W3C · 1.2 since 2003

A strict XML messaging protocol. The contract lives in a WSDL file, and the WS-* stack adds security, reliable delivery and transactions.

REST

Fielding · 2000

An architectural style, not a product. Data becomes resources with URIs; HTTP verbs and status codes carry the operation and the outcome.

GraphQL

Meta · open since 2015

A typed schema plus a runtime. The client sends a query describing exactly the fields it wants, and gets back that shape and nothing more.

gRPC

Google · 2015

Remote procedure calls over HTTP/2. Messages are binary Protocol Buffers, and both client and server stubs are generated from a .proto file.

Trade-offs

Advantages and limitations

What it gives youWhat it costs you

SOAP

  • Formal, machine-readable contract
  • Standards for message-level security, reliable delivery and distributed transactions
  • Independent of the transport
  • Verbose and slow to parse
  • Steep learning curve, heavy tooling
  • Poor fit for browsers and mobile networks

REST

  • Simple, ubiquitous, easy to test with a browser or curl
  • Caching, proxies and CDNs work out of the box
  • Stateless, so it scales horizontally
  • No contract unless you add OpenAPI
  • Over-fetching and under-fetching
  • Related data can take several round trips

GraphQL

  • The client asks for exactly the fields it needs
  • One endpoint covers many resources
  • Typed and self-documenting through introspection
  • HTTP caching is lost
  • N+1 resolver problem without a data loader
  • Deep queries need depth and complexity limits

gRPC

  • Highest throughput and lowest latency
  • Type-safe generated stubs in many languages
  • Streaming, deadlines and cancellation are first class
  • Binary payloads are hard to read while debugging
  • Needs a proxy to reach a browser
  • Requires HTTP/2 all the way through

Case study

Student Management System

The right architecture depends on the clients, the shape of the data and the traffic. Here is the profile we designed against.

Core resources

Students, lecturers, courses, class sections, enrollments, grades, transcripts and timetables. Almost every entity is a record that is created, read, updated and listed.

Clients

A student web portal, a staff admin portal, a mobile app, and third-party campus systems such as the LMS, the library and a payment gateway.

Traffic

Read-heavy. Course catalogue, timetable and grade lookups dominate day to day, while writes arrive in short bursts during the enrollment window each semester.

What matters most

Easy integration for other campus systems, low development and maintenance cost, effective caching, standard authentication, and documentation a new developer can follow.

No requirement here calls for distributed transactions, message-level signing, sub-millisecond latency or long-lived streams — which is what rules three of the four candidates out.

Decision

We chose REST over HTTPS with JSON, described by an OpenAPI 3.1 contract.
  1. The domain is already resource-oriented. Students, courses and enrollments map onto URIs and HTTP verbs with almost no translation.
  2. Read-heavy traffic gets caching for free. Catalogues and timetables change rarely, so ETag and Cache-Control let browsers and proxies absorb most reads.
  3. Every client can reach it. Web, mobile and external campus systems all speak plain HTTP — no proxy and no special client library.
  4. Lowest cost to build and hand over. Spring Boot plus springdoc-openapi gives a documented, testable API in days.
  5. Standard security and ecosystem. TLS, OAuth2 and JWT, role checks per endpoint, and mature tooling: Swagger UI, Postman, gateways, rate limiting.
  6. Fast enough. Payloads are small records, not high-frequency streams, so REST's overhead is irrelevant at campus scale.

Why not SOAP

Its transactional and message-security guarantees are not needed here, and the XML overhead hurts exactly the mobile clients we care about.

Why not GraphQL

Its flexibility pays off with many heterogeneous sources, and it would cost us the HTTP caching this read-heavy system depends on.

Why not gRPC

Excellent between internal services, but a poor public edge: browsers need a proxy and the binary format is hard to debug or integrate with.

The honest trade-off. REST over-fetches and can need extra round trips. We mitigate that with sparse fieldsets, sub-resource endpoints, pagination and optional expansion. If the mobile app later needs highly variable payloads, a GraphQL gateway can sit in front of the same services.

Resource and endpoint design

Base URL https://api.university.edu/v1

GET/students?major=SE&page=0&size=20List and filter students, paginated
GET/students/{studentId}Read one student
POST/studentsCreate a student
PATCH/students/{studentId}Update part of a student record
GET/students/{studentId}/enrollments?semester=FA26The courses a student is taking
GET/courses/{courseId}Course details and available sections
POST/enrollmentsEnroll a student in a class section
DELETE/enrollments/{enrollmentId}Drop a course
GET/students/{studentId}/transcriptComputed transcript with GPA and credits

Conventions: plural nouns and no verbs in the path, the HTTP status code carries the outcome, application/json for payloads, application/problem+json for errors, and a bearer token on every call.

The contract: OpenAPI 3.1

openapi: 3.1.0
info:
  title: Student Management API
  version: 1.0.0
servers:
  - url: https://api.university.edu/v1
paths:
  /students/{studentId}:
    get:
      summary: Get a student by ID
      security: [{ bearerAuth: [] }]
      parameters:
        - name: studentId
          in: path
          required: true
          schema: { type: string, pattern: '^[A-Z]{2}\d{6}$' }
      responses:
        '200':
          description: Student found
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Student' }
        '404': { description: Student not found }
components:
  schemas:
    Student:
      type: object
      required: [studentId, fullName, major, status]
      properties:
        studentId:      { type: string, example: 'SE170123' }
        fullName:       { type: string }
        email:          { type: string, format: email }
        major:          { type: string }
        enrollmentYear: { type: integer, minimum: 2000 }
        status:
          type: string
          enum: [ACTIVE, SUSPENDED, GRADUATED]
  securitySchemes:
    bearerAuth: { type: http, scheme: bearer, bearerFormat: JWT }

REST has no built-in contract

That is its main weakness next to SOAP and gRPC, where the contract is part of the protocol. OpenAPI closes the gap without giving up plain HTTP.

What the contract buys us

  • Interactive documentation through Swagger UI
  • Generated client SDKs for the mobile app and partner systems
  • Request and response validation at the gateway
  • A single artifact to review when the API changes

In Spring Boot the file is generated from the controllers by springdoc-openapi, so the documentation cannot drift away from the code.

Conclusion

What we take away

  • The four architectures solve different problems: SOAP gives contracts and enterprise guarantees, REST gives simplicity and reach, GraphQL gives client-driven queries, gRPC gives speed and streaming.
  • There is no universally best option. The choice follows the clients, the shape of the data and the traffic profile.
  • For a Student Management System, REST wins on client reach, cacheability and cost of development, and its weaknesses are cheap to mitigate.
  • A real system can mix them: keep REST at the public edge, add gRPC between internal services once the system is split into microservices, and put a GraphQL gateway in front if mobile clients need highly variable payloads.

Appendix

The same request in the other three

Reading student SE170123, expressed in SOAP, GraphQL and gRPC.

SOAP message

<soap:Envelope
  xmlns:soap="http://www.w3.org/2003/05/soap-envelope"
  xmlns:sms="http://university.edu/sms">
  <soap:Header/>
  <soap:Body>
    <sms:GetStudentRequest>
      <sms:StudentId>SE170123</sms:StudentId>
    </sms:GetStudentRequest>
  </soap:Body>
</soap:Envelope>

The operation name lives in the body, not in the URL. Every call is a POST to one endpoint.

GraphQL query

query StudentWithEnrollments($id: ID!) {
  student(studentId: $id) {
    fullName
    major
    enrollments(semester: "FA26") {
      status
      course {
        code
        title
        credits
      }
    }
  }
}

One round trip returns the student and the nested course data — what REST would need two or three calls for.

gRPC service definition

syntax = "proto3";
package sms.v1;

service StudentService {
  rpc GetStudent (GetStudentRequest)
      returns (Student);
  rpc ListEnrollments (ListEnrollmentsRequest)
      returns (stream Enrollment);
}

message GetStudentRequest {
  string student_id = 1;
}

message Student {
  string student_id      = 1;
  string full_name       = 2;
  string major           = 3;
  int32  enrollment_year = 4;
}

Field numbers, not names, travel on the wire — which is what keeps the payload small and the schema compatible.
